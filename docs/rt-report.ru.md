# Лабораторный отчёт: распределения времени выполнения и пригодность для реального времени

**Стенд:** Radxa Dragon Q6A (QCS6490), Hexagon v68 CDSP + Cortex-A78.
**Дата измерений:** 2026-11-14 UTC.
**Сырые данные:** `results/rt-2026-11-14/raw/`.
**Машинная сводка:** `results/rt-2026-11-14/summary.md` (генерируется `tools/rt_analyze.cpp`).
**English summary:** [`rt-report.md`](rt-report.md).

|---|---:|---:|---:|
| CPU A78, idle | годен | годен | годен |

«Годен» здесь — эмпирический критерий по p99.9 и наблюдаемому max, не гарантия WCET.

## 1. Цель и гипотезы

Цель — измерить не только медиану, но распределение времени FOC-шага, хвосты и
пригодность вариантов CPU и DSP+RPC для трёх периодов управления: 100 мкс
(10 кГц), 50 мкс (20 кГц) и 20 мкс (50 кГц).

Гипотезы и критерии были зафиксированы до прогонов:

- **H1.** CPU A78, привязанный к CPU 7, укладывается в 20 мкс по p99.9.
- **H2.** DSP compute-only (без RPC на каждый шаг) укладывается в 20 мкс по p99.9.
- **H3.** DSP + один FastRPC `step` на шаг **не** укладывается в 100 мкс по p99.9:
  медиана RPC около 70 мкс, хвост ожидается выше 100 мкс.
- **H4.** Нагрузка на CPU и память увеличивает хвост DSP+RPC; сильнее всего —
  нагрузка на память.
- **H5.** Работа DSP не замедляет CPU 7 заметно, если CPU-поток привязан к CPU 7.

Критерий пригодности (до прогонов): **годен**, если p99.9 < периода и
наблюдаемый максимум < периода; **условно**, если p99.9 < периода, но
наблюдаемый максимум ≥ периода; **не годен**, если p99.9 ≥ периода.
Наблюдаемый максимум — не WCET и не гарантия.

## 3. Методика

### 3.1. Сырые выборки

- **DSP:** в скелет добавлен `sampler_run(batch_steps, sample_count, ...)`. Он
  выполняет `sample_count` батчей по 16 шагов и сохраняет циклы каждого батча в
  статический массив `uint16_t[100000]` на DSP. Хост выгружает массив
  скалярными вызовами `sampler_get(idx)`, поэтому контракт «только скалярные
  аргументы» не нарушается. Массив статический: динамическое выделение через
  `realloc` не загружалось на CDSP.
- **Хост:** `rt-step` измеряет каждый RPC `step` через
  `clock_gettime(CLOCK_MONOTONIC_RAW)`; `rt-cpu` — батч из 16 CPU-шагов;
  `rt-bench` — RPC `bench` с 16 шагами.
- **Батч RPC:** `rt-bench` вызывает `bench(warmup=0, runs=1, iterations=16)`,
  то есть один RPC на 16 шагов. Это не то же самое, что один RPC на шаг.
- **Тёплый старт:** первые 100 выборок каждого файла помечены `warmup=1` и
  исключены. Для `DSP + FastRPC step` после обнаружения дрейфа измерение
  повторено с `warmup=1000`; в таблицах для этого варианта N=102000, для
  остальных — 101700.
- **Число выборок:** 34 000 × 3 раунда на конфигурацию (102 000 до вычета
  warmup); `bench` — 10.5k × 10 чанков (105 000, после warmup 104 000).
- **Чередование:** в каждом раунде варианты шли в порядке CPU → DSP compute →
  DSP+RPC step, затем следующий раунд. Это снижает риск приписать дрейф
  температуры одному варианту.
- **Условия:** `idle`; `cpu-load` — stressor из соседнего ResNet-50 репозитория
  (2 воркера, CPU 4–5, повтор по 10 с); `memory-load` — 2 потока чтения-записи
  по 256 МиБ, CPU 4–5; `dsp-load` — фоновый цикл `bench` на DSP, измеряется CPU.

### 3.2. Учёт накладных расходов таймера

Стоимость чтения таймера измерена отдельно (L6) и **вычтена** из всех значений:

- CPU: `clock_gettime` — 40.143 нс/вызов; в батче два вызова, то есть
  80.286 нс на выборку (5.018 нс/шаг при batch=16).
- DSP: `qurt_get_core_pcycles` — 24.015 циклов/вызов; в батче два вызова,
  то есть 48.03 циклов на батч (3.00 цикла/шаг при batch=16).

Сырые CSV не содержат вычитания; коррекция выполняется анализатором. Значения
ниже разрешения таймера не интерпретируются.

### 3.3. Показатели

Для каждой конфигурации: min, p50, p90, p99, p99.9, p99.99, наблюдаемый max,
IQR = p75 − p25, jitter = p99 − p50. Среднее и стандартное отклонение не
используются как главные метрики. p99.99 показывается только при N ≥ 100 000.

Доверительные интервалы — бутстреп, 1000 повторных выборок, 95%. Сравнения
вариантов — отношение медиан и разности медиан/p99 с интервалами; критерий
Манна–Уитни не использовался.

### 5.5. Влияние нагрузок на хвост

- **CPU load** почти не меняет p50 DSP+RPC (71.5 → 72.0 мкс), но p99 растёт
  361.6 → 459.3 мкс, p99.9 — 1.046 → 0.611 мс (немонотонно из-за хвоста).
- **Memory load** сильнее всего: p50 122.3 мкс, p99 1.22 мс, p99.9 1.454 мс,
  max 27.26 мс; 100% выборок выше 100 мкс. Это ключевой риск для DSP+RPC.
- **DSP load** не меняет медиану CPU (56.9 нс) и p99 (66.6 нс); хвост
  p99.9 431 нс, max 50.4 мкс. Обратное влияние DSP на CPU 7 в медиане
  отсутствует; хвост требует отдельного исследования.
- **CPU compute-only** стабилен: p99.9 366–367 нс во всех условиях; нагрузка
  на CPU/память не меняет вычисление DSP заметно.

### 5.6. Дрейф и временной ряд

Для DSP+RPC step после warmup=1000 линейный тренд −1.23% за серию; для CPU

Остаточный тренд описан, но не корректировался.

## 6. Обсуждение

1. **DSP compute-only быстр по абсолютной величине, но не быстрее CPU.**
   330 нс/шаг против 56.9 нс; отношение 5.81×. Это подтверждает вывод
   финального отчёта: для данного скалярного FOC DSP не является ускорителем.
2. **FastRPC полностью доминирует в реальном контуре.** Один RPC `step` стоит
   ~71.5 мкс медианы, то есть в ~216× больше самого DSP-вычисления. Пакетный
   `bench` на 16 шагов даёт ~5.1 мкс/шаг, но это уже другой контур управления:
   один RPC на 16 шагов, а не на каждый шаг.
3. **Для периода 100 мкс DSP+RPC не годен даже в покое:** 2.29% выборок выше
   периода, p99.9 ≈ 1.05 мс. Под нагрузкой на память — 100% выше 100 мкс.
4. **CPU A78 укладывается в 20 мкс по p99.9 во всех условиях**, но под
   cpu-load есть единичные выбросы до 181 мкс; поэтому формально «условно».
   Для жёсткого реального времени нужен watchdog/бюджет на выбросы, а не
   только p99.9.
5. **DSP не мешает CPU 7 в медиане.** Обратное влияние не обнаружено; хвост
   50 мкс под dsp-load требует отдельного объяснения (вероятно, общие
   прерывания/планировщик, а не DSP-вычисления).

## 7. Угрозы достоверности

- Одна плата, один экземпляр QCS6490, один SDK 6.4.0.2; перенос на другую
  плату/прошивку не гарантирован.
- Энергия/мощность не измерялись: нет внешнего измерителя (см.
  `docs/energy-and-power.md`).
- Наблюдаемый максимум не является WCET; p99.9 — эмпирическая оценка.
- Температура доходила до 90.7 °C; отдельного контроля троттлинга нет,
  хотя governor `performance` и частоты фиксировались.
- CDSP PD в ходе длительных прогонов один раз уходил в `offline` (open error
  114); помогал только reboot. Поэтому `bench` собран чанками по 10.5k
  вызовов, а не одним процессом на 100k.
- 41 IRQ не удалось перенести с CPU 7; `isolcpus` отсутствует. Полная
  изоляция ядра не достигнута.
- Для CPU под cpu-load один выброс 181 мкс определяет вердикт «условно»;
  это реальный наблюдаемый хвост, но его причина не локализована.
- Сравнение DSP/CPU в этом отчёте использует инструментальный батч и
  коррекцию таймера; оно не тождественно финальному отношению 5.28×.

## 8. Выводы

- Для FOC с одним FastRPC-вызовом на шаг **DSP+RPC не пригоден** для периодов
  100/50/20 мкс: p99.9 превышает период во всех условиях, а под нагрузкой на
  память превышение практически тотальное.
- **DSP compute-only пригоден** по p99.9 для всех трёх периодов, но его
  медиана в 5.81× хуже CPU; сам по себе он не даёт выигрыша.
- **CPU A78** пригоден для 20 мкс по p99.9 в покое и под памятью; под
  cpu-load формально «условно» из-за редких выбросов.
- Чтобы DSP+RPC стал пригоден для 100 мкс, нужно либо убрать RPC с горячего
  пути (разделяемая память/очередь), либо батчить шаги, либо переносить
  управление на CPU. Пакетный `bench` показывает, что вычисление не является
  узким местом; узкое место — транспорт.
